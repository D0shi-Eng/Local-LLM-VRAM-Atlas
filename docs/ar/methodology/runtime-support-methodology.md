# منهجية دعم التشغيل

> المقابل الإنجليزي: `docs/en/methodology/runtime-support-methodology.md`

## لا رقم VRAM دون runtime

يستهلك المُخرَج نفسه كميات مختلفة من VRAM تحت llama.cpp وExLlamaV2
وTensorRT-LLM وTransformers وMLX وOllama وLM Studio. فعبارة «VRAM النموذج» دون
بيئة التشغيل وإصدارها وواجهتها وسياقها ووضع إزاحتها عبارة ناقصة، لذا يرتبط كل
تقدير بملف `RuntimeMemoryProfile` (`memory/runtime_profiles.py`): سلوك تحميل
الأوزان، ونوع ذاكرة التخزين المؤقت وتكميمها، وسلوك مساحة العمل والرسم، وأي
عبء تشغيلي **مقاس** بمصدره. والعبء التشغيلي غير المقاس يبقى `unknown`، ولا
يُستعاض عنه بثابت بديل مثل `500 MB` أو `1 GB`.

## المحركات والواجهات والعتاد

منتجات الواجهة ليست محركات: فقد يستخدم LM Studio واجهات مختلفة ويثبت
Ollama بنية محرك معينة، فيُسجل المحرك والواجهة متى عُرفا. ودعم الصيغة لا
يعني دعم العتاد الشامل أبدًا: فدعم NVFP4/MXFP4 يعتمد على النموذج ونسخة
التشغيل والنواة وجيل GPU، ويُسجل مع `observed_at` ومراجعة المصدر لأن
المصفوفات تتغير. وكذلك وجود نقطة فحص AWQ/GPTQ لا يعني أن كل تشغيل يديرها:
فصيغة الـartifact ودعم بنية النموذج ودعم نواة GPU ثلاثة ادعاءات منفصلة.

## ملفات موثقة بحدود صادقة

يشحن المشروع ملفات هندسية صريحة (llama.cpp/CUDA بإزاحة كاملة، و
ExLlamaV2/CUDA وذاكرة MLX الموحَّدة؛ وأحمالها الزائدة فيها مجهولة بالتصميم. وغياب
بيئة تشغيل من المستخدم يعطي المكوّنات المستقلة فقط؛ ولا بيئة تشغيل افتراضية
صامتة أبدًا.
